# How it works

The five-stage pipeline that turns a TypeScript router into generated Dart bindings, and how the Dart runtime executes them.

← Previous: Quickstart | Next: Type mapping →

## Build time: the Node.js compiler

### Stage 1 — Route discovery

The CLI spawns the router module in an isolated sandbox and walks the live router object: tRPC v11 exposes a flat `_def.procedures` map keyed by full dot-paths (`user.getById`, `posts.list`). Procedure kinds (`query` / `mutation` / `subscription`) and `.meta()` values (`access: 'authenticated'`, tags) come from each procedure's definition.

### Stage 2 — ts.TypeChecker virtual harness

The CLI writes an in-memory harness module into your program (nothing on disk):

```typescript
import type { appRouter } from './src/trpc/router';
import type { inferRouterInputs, inferRouterOutputs } from '@trpc/server/unstable-core-do-not-import';

export type __rpc_dart_inputs = inferRouterInputs<typeof appRouter>;
export type __rpc_dart_outputs = inferRouterOutputs<typeof appRouter>;
export type __p_user_getById_in = __rpc_dart_inputs['user']['getById'];
```

One alias pair per procedure forces indexed-access evaluation so the `ts.TypeChecker` hands over concrete types. Input types carry `z.input` semantics (what the client sends), outputs carry `z.output` semantics (what the client receives) — this is why Zod `.transform()` never corrupts your models.

### Stage 3 — Contract IR

The checker types are classified into a normalized, language-independent contract: procedures, a type registry (objects, enums, unions, records, tuples, sets), optionality/nullability flags, and metadata. Everything is serialized with recursively sorted keys and hashed with SHA-256.

### Stage 4 — Dart emission

The emitter is a pure function from the contract to Dart text. Files are written atomically (`write.tmp` → rename) into `lib/src/api/`:

```dart
// Generated by rpc-dart 0.1.0 (contract sha256-41728e69…). DO NOT MODIFY.
class UserGetByIdOutput {
  factory UserGetByIdOutput.fromJson(Map<String, Object?> json) => UserGetByIdOutput(
        id: RpcJson.requiredField(json, 'id', RpcJson.asString, model: 'UserGetByIdOutput'),
        ...
      );
}
```

The manifest (`generated.rpc-dart.json`) records the contract hash, every emitted file with its content hash, and any recorded diagnostics.

### Stage 5 — Hash-gated regeneration

On every TypeScript save, the watcher re-extracts and compares the contract hash. Unchanged contracts touch nothing; changed contracts re-emit atomically and delete stale files listed in the old manifest. That is how renaming a procedure removes `user_get_by_id.dart` and makes `flutter analyze` fail at every stale call site.

## Runtime: the Dart engine

### Links pipeline

```dart
LoggingLink → AuthLink → ContextLink → RetryLink → TransformLink → HttpBatchLink
```

- `AuthLink` attaches credentials and performs single-flight token refresh: N concurrent 401s produce exactly one refresh, then one bounded replay each.
- `RetryLink` retries eligible queries with exponential backoff; mutations never retry without an idempotency key.
- `HttpBatchLink` coalesces same-tick calls into one request, splits oversized GET batches, and demultiplexes the index-aligned responses (including Fastify's 207 multi-status).

### SuperJSON + RpcJson decoding

The transport decodes the SuperJSON envelope (`{json, meta.values}` with flat dotted-path annotations for `Date`, `bigint`, `set`, `map`, NaN/Infinity) into a Dart-native tree (`DateTime`, `BigInt`, `Set`, `Uri`). Then the generated `fromJson` runs **zero-cast decoding** via `RpcJson`: every field is pattern-matched, and failures throw a typed `RpcDecodeException` with the breadcrumb (`UserGetByIdOutput.items[0].title`), expected and actual types — never a raw VM `TypeError`.

### Query cache

`RpcQueryCache` stores decoded models keyed by structural `RpcQueryKey`s. Invalidation is typed and prefix-based (`api.user.pathKey`), watchers re-emit automatically, and `trpc_flutter` bridges refs to native `ValueListenable`s.
